# FanHua 单模型双游戏主线训练清单

日期：2026-10-08  
目标：使用原 WemiEnv 训练并验收**一份**同时掌握 Flappy Bird 和 Timberman 的 PyTorch 共享模型。

## 一、先把目标和实验范围定死

本次交付物只有一份主模型检查点。它包含共享 actor、双 Q critic、目标网络、动作表示原型、优化器状态、回放状态、随机数状态和训练阶段信息。训练时切换游戏不重新初始化；最终加载同一个 `.pt` 文件分别连接两款游戏。

当前不执行 9 个实验组，也不执行 18 次两种子正式对照。那些配置用于论文式消融和稳定性研究，服务于“分析每个组件的贡献”，不是得到一份双游戏模型的必要条件。它们保存在 `configs/prerequisites_v2` 和 `reports/前置工作验收.json` 中，状态保持 `held`，不与主线运行混淆。

当前主线采用“已有共享候选模型续训”方案，而不是把 Flappy Bird 和 Timberman 两份单游戏模型拼接。续训起点是：

`experiments/20261006_171810_268739_repair_shared_policy/checkpoints/latest.pt`

这份检查点已经在两款游戏各完成 20 局、每局 300 步的短程测试，但这不是长程精通证明。它含行为约束、输入聚焦和教师路径，属于工程候选模型；因此最终报告必须明确它不是论文原方法的严格复现。原检查点永不覆盖，主线另建新实验目录。

## 三、论文方法在主线中如何落地

论文研究的是动作集合逐阶段扩展；当前两个游戏各自固定为两个离散动作，所以本项目是**参考 Cal-LAICA 机制的跨游戏持续学习扩展**，不是论文的原样复现。

主线保留以下机制：

1. **潜在动作表示**：共享策略先在低维潜在空间产生动作表示，再映射到当前游戏的离散动作。
2. **SAC 与双 Q critic**：用当前和目标 critic 学习策略及动作价值。
3. **价值校准**：对完整自然终止轨迹使用 MC 回报作为参考下界，抑制动作表示价值被过度低估；截断或断线轨迹不冒充完整回合校准数据。
4. **Offline/Online 混合回放（OORB 风格）**：切换游戏后保留旧游戏历史池，同时采样当前池，降低学习第二款游戏时的遗忘风险。
5. **初始行为指导**：当前续训起点已经使用过教师行为约束；主线会记录教师文件和 SHA256，部署时仍只有共享 actor，不调用教师。

需要明确的边界：论文的“动作集合变化”不是本项目的“游戏切换”；论文的理论遗憾界不能直接保证 Flappy Bird 或 Timberman 的成功；行为约束和 Timberman 输入聚焦是本项目的工程扩展，不是 Cal-LAICA 原始项。

## 四、主线正式步骤

### 第 0 步：冻结主线方案，不训练

**做法**

- 复制并校验续训起点的 `.pt` SHA256。
- 新建主线配置，明确 `resume_checkpoint`、单一运行目录、任务顺序、预算和教师来源。
- 保留 `behavior_weight`、校准、历史回放和输入聚焦的实际设置；任何改动都要新建版本，不覆盖旧配置。
- 运行配置检查、路径检查、检查点可加载检查和自动验证。

**预期产物**

- `FanHua/experiments/<主线目录>/config.json`
- `source_checkpoint.json`（起点路径、SHA256、参数摘要）
- `preflight.json`（门禁结果）

**通过条件**

- 起点检查点可加载；模型结构和配置一致；没有活动训练进程；旧目录只读保留。

### 第 1 步：起点双游戏长程验收

在续训前先对现有候选做一次不更新参数的长程测试，避免把短程通过误认为已经足够好。

**做法**

- Flappy Bird：20 局，每局最多 3000 步。
- Timberman：20 局，每局最多 3000 步。
- 两款游戏使用同一个起点 `.pt`；评估前后比较参数哈希和更新计数。

**预期产物**

- 两个独立评估目录、逐局日志、均值、标准差、自然终止数、预算截断数、动作统计和参数不变证明。

**通过条件**

- 协议稳定、模型不会在评估中更新；两款游戏结果达到或接近单游戏基线；没有一款游戏出现明显崩溃。

**失败处理**

- 只保留结果并记录失败原因；从原起点复制出修复候选，不能覆盖起点。
- 若 Flappy Bird 仍持续不跳，优先检查动作映射、行为约束和动作原型；若 Timberman 换边危险，检查动作时序和碰撞后的方向语义。

### 第 2 步：运行短程主线冒烟测试

**做法**

- 仍使用主线配置，但把每个阶段缩短为预先登记的小预算。
- 按正式顺序切换游戏，确认检查点保存、阶段恢复、历史池和单个窗口连接正常。
- 本次冒烟预算固定为 Flappy Bird → Timberman → Flappy Bird → Timberman，各 768 步，共 3072 步；训练单局最多 256 步，以便及时入池并验证多次更新。每段当前游戏评估 5 局、每局最多 300 步。
- 冒烟使用原起点的独立副本；结束后另用同一冒烟最终检查点评估两个游戏，不能把各阶段不同快照的成绩当成最终双游戏能力。

**预期**

- 至少完成一次 Flappy Bird → Timberman 的真实切换；日志能区分训练步、更新次数、阶段评估和断线恢复。

**通过条件**

- 没有观测长度错误、奖励累计错误、多窗口消息或检查点损坏；若失败，主线长程不启动。

### 第 3 步：主线长程训练

每次只训练这一份共享模型，阶段之间不重新初始化：

```text
阶段 1：Flappy Bird 20,000 步
阶段 2：Timberman   20,000 步
阶段 3：Flappy Bird 20,000 步
阶段 4：Timberman   20,000 步
总计：两款游戏各 40,000 步，共 80,000 个真实交互步
```

**每一步的实际过程**

```text
读取 WemiEnv 观测
→ 共享 actor 选择潜在动作并映射为游戏动作
→ 客户端执行动作并返回下一观测、奖励、终止状态
→ 写入当前经验池
→ 按当前/历史比例采样并更新 critic、actor、温度和校准项
→ 定期保存检查点和日志
```

**每 4000 步检查**

- 全局步数、当前阶段、真实更新次数；
- 最近回合步数、回报和死亡/截断；
- actor/critic 损失、梯度是否有限；
- 当前池和历史池数量；
- 最新检查点路径和 SHA256；
- 是否有客户端断线或停止请求。

**每阶段结束**

- 保存 `stage_XX.pt` 和 `latest.pt`；
- 做 5 局、每局最多 300 步的阶段评估；
- 记录当前游戏成绩及之前游戏成绩，计算遗忘趋势；
- 等我确认日志和检查点完整后再切换客户端。

### 第 4 步：最终独立评估

训练结束后复制最终检查点到独立评估流程，训练服务退出或隔离；评估轨迹不写入回放池。

**做法**

- 两款游戏各 20 局，每局最多 3000 步；
- 每局结束反馈局号、步数、回报/得分、自然终止或达到上限；
- 检查评估前后参数 SHA256、更新计数和 `.pt` 文件一致。

**预期产物**

- `final_evaluation_flappybird/evaluation.json`
- `final_evaluation_timberman/evaluation.json`
- 逐局 CSV、动作计数、参数冻结证明和最终成绩表。

### 第 5 步：主模型验收与总结

验收不只看最高分，至少包括：

- 两款游戏的平均表现和标准差；
- 20 局中达到 3000 步上限的比例；
- 自然死亡和异常断线数量；
- 学习第二款游戏前后第一款游戏的性能差异；
- 评估期间参数完全不变；
- 最终 `.pt`、配置、日志和 SHA256 可复现。

“精通”的工程判断暂定为：两款游戏都达到预先记录的长程目标，并且没有明显的跨阶段灾难性遗忘；若只有一款达到上限，结论只能写“部分掌握”，不能宣布双游戏精通。阈值会在第 0 步冻结，不能看完结果后临时修改。

## 五、你需要怎样配合

每次我启动或重启服务后：

1. 我先告诉你监听端口和当前游戏。
2. 你关闭另一款游戏的调试窗口，只保留指定项目。
3. 你点击一次“编译”。
4. 编译后保持模拟器运行，不再次编译、不切换项目，直到我通知阶段结束。
5. 如果控制台出现红色错误，把完整文字发来；不要自行反复编译。
6. 我会主动报告每 4000 步、每阶段完成和每个评估局的结果。

同一端口 `7891` 不能同时连接两个游戏。切换阶段时必须由我先停止旧服务、启动新服务，再由你编译下一款游戏。

## 六、可能的问题和处理原则

| 问题 | 处理 |
|---|---|
| 未连接 | 确认监听后是否编译、是否只有一个窗口；保存并重启当前阶段 |
| Flappy Bird 一直不跳 | 检查动作映射、原型、教师约束和动作计数；回退到上一个检查点做分支修复 |
| Timberman 快速死亡 | 检查左右动作语义、碰撞时序和换边逻辑；不要只凭动作编号推断安全性 |
| 学第二款后第一款退步 | 查看历史采样比例、阶段评估和回放池；从退步前检查点分支，不覆盖成功阶段 |
| 损失/梯度异常 | 暂停并保存诊断；检查奖励缩放、校准数据和学习率，不悄悄延长预算 |
| 断线或人工停止 | 使用 `latest.pt` 连同优化器、回放和随机状态恢复；重新编译后继续 |
| 评估成绩好但参数变化 | 评估不合格，检查是否误用了训练入口；重新做冻结评估 |

所有失败、断线和修复版本都保留，不能只留下最好成绩。

## 七、当前明确不做的事情

- 不启动 `seed2`。
- 不启动 9 组 × 2 种子的 18 次论文式对照。
- 不把单游戏 checkpoint 合并成共享模型。
- 不把旧 PPO 或教师模型用于部署动作选择。
- 不修改原 WemiEnv 游戏客户端。
- 不在没有起点长程验收和短程冒烟证据前直接开始 80000 步长训。

## 八、完成后的最终文件

主线结束后，`FanHua/experiments/<主线目录>/` 应至少包含：

- 一个最终 `checkpoints/latest.pt` 和各阶段 `stage_XX.pt`；
- 冻结的 `config.json`、起点 SHA256 和 `preflight.json`；
- `status.json`、`episodes.csv`、`updates.csv`、协议与事件日志；
- 四个阶段评估结果；
- 两款游戏的独立最终评估目录；
- 一份中文总结，说明论文机制、真实训练预算、结果、遗忘、失败记录和限制。

最终报告会明确区分：共享模型实际成绩、单游戏基线成绩、论文机制的工程迁移，以及“已知两款游戏能力”与“未见游戏泛化”之间的边界。
